## Review Findings

### 1. Backend Correctness ✅

**Delta Derivation Logic**
- Chronological ordering by date: verified.
- First entry 0.0 → account open marker, correctly omitted (prev_cumulative anchored).
- First entry ≠ 0.0 → initial contribution, correctly derived as (value - 0).
- Subsequent deltas: `round(cumulative - prev_cumulative, 2)` — precise.
- Zero deltas: correctly omitted throughout.
- Sign-to-type mapping: positive → "contribution", negative → "withdrawal" — semantically correct.
- No double-counting: each pair of consecutive entries generates exactly one delta.

**Multi-Account Aggregation**
- Verified at two points: `_aggregate` (service.py) and `get_portfolio` (indexa.py).
- **Critical correctness:** Sums `amount` (deltas) by date, NOT per-account cumulatives.
  - Per-account cumulatives have different base points → summing them is mathematically incorrect (wrong baseline).
  - Summing deltas is correct: aggregated cumulative = integral of combined flow.
- Discard per-account cumulatives explicitly.
- Recalculate running total as cumulative sum of combined deltas in chronological order.
- Re-derive type from combined amount resultant.
- Dates with net-zero sum omitted.
- Result: Correct aggregation semantics verified ✅

### 4. Withdrawal Semantics ✅

**Definition Verified**
- Decrease in `net_amounts` → `amount < 0` → `type = "withdrawal"`.
- Correct: cumulative decreases, so delta is negative.
- Tests TC-3, TC-8, TC-11 (and variants) explicitly exercise withdrawals.
- No sub-typing: Indexa API does not distinguish withdrawal types (partial, total, fees). Single "withdrawal" type is correct per API contract.

**Known Limitation (Acceptable)**
- Same-day netting: Multiple movements on same day are netted into single net_amounts entry.
  - Result: Cannot recover individual same-day transactions from delta alone.
  - Tradeoff: Aligns with Indexa API granularity, acceptable limitation documented in contract.
